# repl-tcp_recvmsg P=40 性能实验记录

日期：2026-10-27
内核：6.8.0-147-generic
环境：master `192.168.30.137`（4 vCPU VM），slave `192.168.30.136`（同宿主 VMware VM）

## 1. 目的

定位 `repl-tcp_recvmsg` 在 P=40 下相对无同步基准的损耗来源，判断能否通过
eBPF 侧优化把损耗压到接近基准。

本轮只测 P=40（P=1 轮间波动太大）；master 固定 core 1，客户端 core 3，
组件 core 0。master 绑核是组件当前的结构性要求，跨核场景不在本轮范围。

## 2. 实验方法

工作负载：`redis-benchmark -p 2000 -c 1 -n 4000000 -P 40 -t set`（绑 core 3），
master `conf/kvstore-none.conf`（`repl_role off`），每轮前清空 master dump 和
slave 数据。每轮 master 重启，组件重启。

变体定义：

| 档 | 内容 |
|---|---|
| S0 | 无组件，纯基准 |
| S1 | kprobe + kretprobe 都挂，但 BPF 程序立即 `return 0`（纯 trap 成本） |
| S2 | 完整入口/出口逻辑（pending/cfg/probe_read/长度判断/seq），**去掉** ring reserve/copy/submit |
| S3 | 完整 BPF + 用户态排空 ring，但**不写从机**（DISCARD 模式） |
| S4 | 当前仓库完整组件 |
| S5 | fexit 单挂载点原型（完整功能，单 trampoline） |
| S6 | S4 + `BPF_RB_NO_WAKEUP`（**无效，见 5.3**） |

组件/变体源码均放在 `/tmp`，本轮没有改动仓库代码（fexit 原型在
`/tmp/fexit_run/`，S1/S2 的 `.o` 在 `/tmp/s1_empty.bpf.o`、`/tmp/s2_noring.bpf.o`，
DISCARD loader 在 `/tmp/discard_run/`）。

## 4. fexit 单挂载点原型

### 4.1 可行性

在 6.8.0-147 上实测：

- BTF 中存在 `tcp_recvmsg_locked`（`linkage=static`，6 个参数）；
- `SEC("fexit/tcp_recvmsg_locked")` 能正常 attach；
- 28/28 次 recv 都拿到 `ret > 0`，`iter_type == ITER_UBUF`。

之前"fexit 被内核 trampoline 限制"的结论在当前内核上不成立（内核已从
6.8.0-137 升到 6.8.0-147，需要重新验证）。

### 4.2 ITER_UBUF 的推进语义（重要）

在 `tcp_recvmsg_locked` 上做 fentry/fexit 对比，1218/1218 次事件一致：

```
入口: ubuf=0x...9010  iov_offset=0    count=1024
出口: ubuf=0x...9010  iov_offset=992  count=32    ret=992
```

即这个内核的 `iterate_ubuf()` 推进的是 **`iov_offset`**，`ubuf` 保持基址不变：

- `iov_offset += ret`，`count -= ret`；
- 因此 fexit 单点取数：`base = ubuf + iov_offset - ret`，长度 = `ret`；
- 当前 kprobe 入口快照 `ubuf` 依然正确；README 里"`iov_iter_advance` 推进 ubuf、
  出口读到 base+ret"的描述在这个内核上不准确，需要修正（kretprobe 需要
  pending 快照的真正原因是 kretprobe 拿不到 `msg` 参数，而不是 ubuf 会移动）。

### 4.3 功能验证

fexit 原型跑 `testcase fill 20000` + 10KB 随机 value + 单条命令：

- 主从 DBSIZE 一致（20002），从库逐 value 校验 20000 条全部通过；
- 10KB value 主从 md5 一致；
- 退出汇总：200001 条记录 / 180000077 字节（P=40 压测时），丢采样 0，
  剩余未发送 0，无 seq 不连续。

功能上可以替代现有 kprobe+kretprobe。

## 5. 分析与结论

### 5.1 损耗归因（以 3.2 交错中位为准）

- **程序逻辑很便宜**：pending/cfg/probe_read/seq 只占约 1.5%；
- **两次 trap 约占 6%**；
- **ring + 用户态转发 + 从机约占 10%**，是最大的一块；
- **fexit 单点净收益约 2.5%**（P=40）；顺序测试里的 +9.3% 受轮间漂移影响，
  不作为可靠结论。

因此：**继续微调 BPF 程序逻辑不会有明显收益**。剩余损耗的大头在 ring/用户态
转发/从机这一侧，以及两次 trap；fexit 只能吃掉 trap 的一部分。

### 5.2 关于 P=1 接近基准

P=1 下每条命令一次 recv，trap 和 ring 的固定成本按命令计更贵，所以 P=1 的
损耗通常不会比 P=40 更小（前一轮会话测得 P=1 约 −20%）。从本轮归因看：

- 即使把 BPF 程序逻辑全部去掉（S2），仍有约 −7%；
- ring + 转发 + 从机是复制本身的工作，不能靠 eBPF 微优化消掉。

所以"只靠改 eBPF 把 P=1 压到接近基准"不现实；可行的方向是 fexit（约 2.5%）
叠加用户态转发路径的优化，或接受复制本身的成本。

### 5.3 `BPF_RB_NO_WAKEUP` 不可用

把 `bpf_ringbuf_submit(rec, 0)` 改成 `BPF_RB_NO_WAKEUP` 后，用户态
`ring_buffer__poll(rb, 20)` 在超时返回时**不会主动排空 ring**，结果是 ring 填满：

```
镜像 0 字节（0 条记录） ... BPF ring 丢采样 195999 条
```

QPS 看起来很高（60–83k），但那是"绝大多数记录被丢弃、不再拷贝"的假数据，
不是有效组件。要正确使用 no-wakeup，必须在用户态补 `ring_buffer__consume()`
（每轮 poll 后主动排空 + 退出前补一次），但这会改变消费模型；本轮不再继续
这条路径。

### 5.4 S3（排空 ring、不转发）异常

3.2 里 S3 明显低于 S4（37.0k vs 46.4k），但 3.3 里 S3 与 S4 接近（53.8k vs
54.9k），不可复现。可能原因：消费者变快后 producer 侧唤醒/IPI 次数变化、
调度抖动、或从机空闲导致宿主 CPU 状态变化。**不把 S3 作为结论依据**；
ring+转发的成本以 S2→S4 的差值（约 10%）为准。

## 6. 后续建议

1. **如果要落地优化，优先把 fexit 单点纳入组件**：功能已验证，P=40 约 +2.5%，
   P=1 可能更高（入口 trap/pending 按命令计）。改动点：
   - `repl-tcp_recvmsg.bpf.c`：`SEC("fexit/tcp_recvmsg_locked")`，用
     `base = ubuf + iov_offset - ret`；
   - `repl-tcp_recvmsg.c`：改为 `bpf_program__attach_trace`，去掉 pending 相关；
   - README 同步修正 `ubuf` 推进的描述。
2. **不要再尝试 no-wakeup + 现有 `ring_buffer__poll(20)`**：功能会失效；
   若要做，需要先设计"超时主动排空 + 退出补排空"的消费模型并重新验证。
3. **ring/转发路径**是剩余大头：可评估用户态直接从 ring 内存 `write`（减少
   `g_pend` 拷贝）、批量写、或把从机移到独立物理机以排除同宿主竞争；这些
   需要单独实验。
4. **测试环境**：两台 VM 在同一物理宿主，从机执行复制命令会与 master 竞争
   宿主资源；不同批次基准在 50–78k 间波动，建议后续固定机器状态、增加交错
   轮次（≥5 轮）再下结论。
