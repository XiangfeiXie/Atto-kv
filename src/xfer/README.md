# xfer — 全量同步两种传输方式的传输速率测试组件

## 一、测试目的

kvstore 里全量同步实测 sendfile **48.65 MB/s**、rdma **206.86 MB/s**。

- rdma 那个已经闭环：与 perftest `ib_write_bw -R` 的 207.97 打平 ⇒ 顶到 `rxe0`
  （soft-RoCE）的软件上限。
- **sendfile 的 48.65 对不上任何已知上限** —— 回环 TCP 1.4 GB/s、`-Z` 2.5 GB/s、
  dd 顺序写 195 MB/s（含 fsync）、64KB 小块 198 MB/s，都已排除。

项目里的代码无法继续拆：sendfile 服务端把 `rdb_save_sync()`（落盘）和传输焊在一起，
客户端收完还要 `rdb_load_from_buf()`（建索引），两端的 IO 都混在测量区间里。

所以把传输本身提取成两个独立组件，喂**同一份 rdb 文件**，把"产生数据"和
"消费数据"这两段干扰排除掉，再逐项定位。

## 二、组件与使用方法

落位 `src/xfer/`，两个**自包含**的 `.c`，各出一个可执行文件，平铺在 `build/`：

- `build/xfer-sendfile` — TCP `sendfile(2)` 零拷贝
- `build/xfer-rdma` — RDMA 单 WR 整块直写

不 include 项目任何头文件，不链 jemalloc / io_uring / 引擎 / ntyco，也不生成 RDB。
结论先在组件上拿到，再决定要不要搬回 kvstore —— 所以这里可以比项目里跑得更纯。

协议：sendfile 是**裸字节 + 关闭**（无握手、无协议头）；rdma 是客户端注册接收缓冲、
把 `{addr, rkey}` 发给服务端，服务端把整个文件作为**一个 WR**
（`IBV_WR_RDMA_WRITE_WITH_IMM`，`imm_data` = 字节数）直写过去。
收发缓冲固定 512 MiB，也就是可传文件的上限，超了**拒绝**、不静默截断。

**顺序要点**：rdma 侧连接就绪（accept + 收到凭证）之后才读文件。读 158 MB 是百毫秒级，
若先读后监听，对端的 REQ 落在监听就绪之前会被丢、双方挂死。

### 编译

```bash
cd /home/xxf/9.1-kvstore/build
cmake .. && make xfer-sendfile xfer-rdma -j"$(nproc)"
```

### 备一份文件

```bash
head -c 158400008 /dev/urandom > /tmp/x.rdb   # 与 kvstore 150000×1024B 快照同尺寸
```

内容无关（纯传输计时与内容无关），但**别用稀疏文件** —— `dd seek=` 造出来的是空洞，
sendfile 会走快路。用 `du` 对一下 apparent size 与实占。

### 跑

```bash
# sendfile
./build/xfer-sendfile server /tmp/x.rdb 2100 &
./build/xfer-sendfile client 192.168.30.137 2100              # 落到 /tmp/xfer_<pid>.rdb
./build/xfer-sendfile client 192.168.30.137 2100 --discard    # 关键对照：只收不落盘

# rdma
./build/xfer-rdma server /tmp/x.rdb 2200 &
./build/xfer-rdma client 192.168.30.137 2200 --discard
```

两个组件都监听端口，**串行跑，不要同时起**。

### 读数

```
[sendfile] xfer-end: bytes=... xfer=...ms rate=...MB/s | tail=...ms
[sendfile] recv-end: bytes=... wait=...ms rate=...MB/s [ (discard)]
[rdma]     xfer-end: bytes=... xfer=...ms rate=...MB/s | prep: conn=...ms read=...ms
[rdma]     recv-end: bytes=... wait=...ms [ (discard)]
```

计时口径三条线统一到"**对端已经拿到**"：

| 线 | 停表在哪 | 含义 |
|---|---|---|
| `xfer-rdma` | `post_send` → send CQE | 对端已 ACK，数据确已写进对端内存 |
| `xfer-sendfile` | `sendfile()` 循环 → `shutdown(SHUT_WR)` → 等到对端 FIN | 对端已把数据全部读走 |
| `iperf3` | 接收端 read 计数 / 墙钟 | 对端已读走 |

sendfile 这侧要特别处理：阻塞 socket 上 `sendfile()` 返回只表示字节进了**本端**发送缓冲，
末段还在途；不等它就停表量到的是"本端交出去有多快"，比 iperf3 的接收端口径虚高 2~5%
（`tail=` 就是这个修正量，≈ 收发缓冲之和 ÷ 速率，与文件大小无关）。
做法是循环结束后 `shutdown(SHUT_WR)`：FIN 排在这批数据之后，客户端收到 EOF 就 `close`，
FIN 回来时本端 `recv` 返回 0。**协议一个字没改。**

| 字段 | 含义 |
|---|---|
| `xfer` / `rate` | **纯传输区间**，口径见上表。十进制 MB/s |
| `tail` | 尾部同步那一段（把口径从"发送缓冲"抬到"对端收完"的修正量） |
| `conn` | 从"可以监听"到"连接可用且对端凭证到手"。**含等对端来连的那段时间**（服务端先起、客户端迟到多久它就有多大）⇒ 不是传输成本 |
| `read` | 服务端把文件读进内存（rdma 要整块发，sendfile 不需要，故只有 rdma 有） |
| `wait` | 客户端墙钟。sendfile 侧与 `xfer` 同口径，用来互相校验；**rdma 侧不是** —— 服务端是"先连后读文件"，客户端的等待里夹着对端读文件的时间，只作参考 |

| 选项 | 端 | 说明 |
|---|---|---|
| `--discard` | 客户端 | 收到即丢、不落盘。**但它同时把"512 MiB 冷缓冲"也摘掉了**（改成收进 64 KB 复用栈缓冲），读的时候按"接收端"整体理解，别只读成"落盘" |

## 三、全量同步速率汇总

150000 键 / 158400008 B。`192.168.30.137` 在本机走 `dev lo`（不出网卡）。

| 传输方式 | 被测项 | 接收侧 | 数据分块 | MB/s | 占本路顶 |
|---|---|---|---|---|---|
| TCP 零拷贝 | iperf3 `-Z -l 1M`（对照顶） | 1 MB 复用缓冲 | 1 MiB | **2138** | 100% |
| TCP 零拷贝 | xfer-sendfile 组件 `--discard` | 64 KB 复用栈缓冲 | 64 KB | 1999.50 | 93.5% |
| TCP 零拷贝 | 项目 sendfile（malloc + 预触） | 512 MB malloc + 预触 | 1 MiB | 1669.22 | 78.1% |
| TCP 零拷贝 | 项目 sendfile（mmap + 大页 + 预触） | 512 MB mmap + MADV_HUGEPAGE + 预触 | 1 MiB | 1613.29 | 75.5% |
| TCP 零拷贝 | xfer-sendfile 组件（落 /tmp） | 64 KB 复用栈缓冲 → 文件 | 64 KB | 399.77 | 18.7% |
| TCP 零拷贝 | 项目 sendfile（旧：落盘 + mmap 加载） | 64 KB 栈缓冲 → 文件 → mmap | 64 KB | 340.25 | 15.9% |
| TCP 零拷贝 | 项目 sendfile（裸 malloc，无预触） | 512 MB malloc，无预触 | 1 MiB | 36.89 | 1.7% |
| RDMA | ib_write_bw `-t 1`（对照顶） | perftest 注册缓冲 | 1 MiB × 1 | **210.29** | 100% |
| RDMA | ib_write_bw `-t 128` | perftest 注册缓冲 | 1 MiB × 128 | 200.07 | 95.1% |
| RDMA | xfer-rdma 组件 | 512 MB 注册缓冲（钉页 = 预触） | 整文件 1 个 WR | 203.36 | 96.7% |
| RDMA | 项目 rdma | 512 MB 注册缓冲（钉页 = 预触） | 整文件 1 个 WR | 201.83 | 96.0% |

1. **`-Z` 才是 sendfile 的对照。** sendfile 把 page cache 的页直接挂进 skb；iperf3 三种
   模式里只有 `-Z`（MSG_ZEROCOPY，省掉"用户态→内核"那次拷贝）落在同一条零拷贝路径上。
   默认内存模式多一次 user→kernel 拷贝（早先 `-t 5` 测得 11.1~11.7 Gbit/s = 1387~1462
   MB/s），`-F` 文件模式还多一次磁盘读（158.4），两者都不是它的对照。
2. **`-O 3` 在这里丢的是最快的一段。** 三轮一致：被 omitted 的前 3 秒是 17.2~18.8
   Gbit/s，之后的 10 秒只有 16.5~18.6 —— 与"跳过硬启动"的预期相反，所以它把上限
   略微**低估**，`-O 1` 即可。
3. **RDMA 侧 WR 深度不是变量。** `-t 1`（1 MiB × 1）与 `-t 128`（1 MiB × 128）六格
   合起来仅 198.18~213.04（中位 209.18，散布 **1.08×**），两组中位差 5% 且区间重叠
   （210.05 已越过 208.30）。⇒ **分块数与队列深度在这条路上测不出方向。**
4. **`BW peak` 列不可用。** 同一份代码同一设备：`-t 1` 的 peak 是 609.21 / 593.07 /
   1248.33，`-t 128` 是 239.37 / 241.43 / 225.81 —— 摆 5 倍且方向反常（浅队列反而更
   高）。只看 `BW average`。
5. **数据规模差异没引入偏差。** perftest 每个配置跑 5000 × 1 MiB = 5.24 GB（约 25 s），
   项目 rdma 每次只搬 158 MB（约 0.78 s），两者仍打平 ⇒ 没有热身效应。
6. **单位必须归一。** iperf3 的 `Gbits/sec` 是 10⁹、`GBytes` 列是 2³⁰（19.4 "GBytes"
   实为 20.85 GB，÷10 s 才等于它自己报的 16.7 Gbit/s）；perftest 是 MB/s（10⁶）。
   不归一就并排，会得出"TCP 比 RDMA 快 84 倍"，实际是 **10.5 倍**。
7. **`-Z` 不是 sendfile 的硬上界。** 早先那格 2500/2575 与本次 2138 是两个参数组
   （`-l` 默认 / 无 `-O` vs `-l 1M` / `-O 3`），不可直接比，本文一律取更保守的 2138。
   但 2500/2575 提醒：`-Z` 自带用户页 pin + zerocopy completion 记账，sendfile 挂的是
   page cache 的页、没有这笔账 —— 它只是最接近的对照，不是天花板。

### 3.2 组件侧

| 腿 | 接收侧 | 数据分块 | MB/s | 占本路顶 |
|---|---|---|---|---|
| `xfer-sendfile --discard` | 64 KB 复用栈缓冲 | 64 KB | **1999.50** | 93.5% |
| `xfer-sendfile`（落 /tmp） | 64 KB 复用栈缓冲 → 文件 | 64 KB | 399.77 | 18.7% |
| `xfer-rdma` | 512 MB 注册缓冲（钉页） | 整文件 1 个 WR | 203.36 | 96.7% |

8. **组件这三条腿是单变量对照：主端是同一份代码、喂同一个文件**，唯一变化的是从端
   把数据往哪放。64 KB 复用栈缓冲 1999.50（93.5%），同一个缓冲再落 `/tmp` 掉到
   399.77（18.7%）⇒ 落盘这一项值 5 倍。
9. **但 `--discard` 不是"只摘掉落盘"的单变量。** 它摘掉的是两件东西：落盘，以及
   "64 KB 热缓冲 vs 512 MiB 冷缓冲"。所以这组数只能说"瓶颈在**接收端把数据往哪放**"，
   不能直接说"瓶颈是落盘"。
10. **`xfer-rdma` 与项目 rdma 打平（203.36 vs 201.83）**，两者接收侧同为 512 MB 注册
    缓冲，而注册（`rdma_reg_write`）本身就把页钉住了 = 自带预触。⇒ RDMA 从端对预触 /
    大页不敏感，与 sendfile 从端的敏感形成对照。
11. **48.65 没有复现**：组件落盘档 228~441，项目侧同口径 340.25，都不在那一档。不再追。

### 3.3 项目侧：把"接收端把数据往哪放"这一格拆开

150000 键 / 158400008 B。**只改从端接收缓冲，主端一行未动。**

（kvstore 的结论行现在尾部带 `| at=MM-DD HH:MM:SS.mmm` 墙钟戳 —— 速率是相对量，
只有配绝对时刻才能把每个数据点对回当时的机器状态。）

| 从端接收方式 | 原始值 (MB/s) | 中位 | 占顶 |
|---|---|---|---|
| 裸 `malloc`，无预触（缺页落在 `recv` 的 copy_to_user 途中） | 36.89 | 36.89 | 1.7% |
| 512 MB `malloc` + 预触 | 1480.90ᵃ / 1356.10 / 1512.24 / 1669.22 / 1705.75 / 1828.62 / 3551.05 | **1669.22** | 78.1% |
| 512 MB `mmap` + `MADV_HUGEPAGE` + 预触 | 1594.14 / 1613.29 / 2141.25 | 1613.29 | 75.5% |
| 旧设计：收进 64 KB 热栈缓冲 → `/tmp` → `mmap` 加载 | 271.58 / 340.25 / 372.37 | 340.25 | 15.9% |
| 项目 rdma（512 MB 注册缓冲 + 整文件 1 个 WR） | 177.50 / 201.83 / 203.75 | 201.83 | 96.0%ᵇ |

ᵃ A/B 交替那一轮的 B 腿（单次）。
ᵇ 对 RDMA 路顶 210.29；其余四行对 TCP 路顶 2138。

12. **主因是"从端接收缓冲的页在不在"，不是"内存 vs 磁盘"。** 裸 `malloc`（36.89）
    **比落盘（340.25）还差 9 倍** —— 落盘那条路收进的是 64 KB 热栈缓冲、从不缺页，
    而裸 `malloc` 把 3.9 万次缺页 + 清零全放在 `recv` 的 `copy_to_user` 里。
    原来那条"内存接收不如落盘"的结论**只在裸 `malloc` 下成立**。
13. **预触是因，它解决的是 40× 那一段。** 同一会话内交替、**两腿同为 4KB 页**
    （`AnonHugePages` 都是 0）、唯一差别是那段触页循环：**36.89 → 1480.90 MB/s，40×**。
    两端计时自洽（差 2.5% / 2.0%），双方都完整加载 150000 键。
14. **大页可以不要，而且它反向印证了剩下的瓶颈。** 4KB 页 + 预触（1669.22）与 2MB 页
    + 预触（1613.29）落在同一散布区间内，大页没有可分辨贡献 —— 不值得为它背上
    `madvise` 和"必须页对齐"的约束，项目侧因此把从端缓冲从 `mmap`+`MADV_HUGEPAGE`
    改回 `malloc` + 预触。**大页能把 12.8 万个页压到 256 个、TLB miss 几乎清零，
    却对 RFO 毫无作用** —— 既然它换不来速率，说明这剩下的差距里 **TLB 不是主成分，
    RFO 才是**（见下条）。
15. **预触只吃到 78.1%，剩下 14.6 个百分点在"目标区冷不冷"。** 组件 `--discard` 与
    项目用的是同一类数据源、同一个 `sendfile()` 循环，却拿到 93.5%，差的这一段只能
    记在从端接收缓冲上：64 KB 复用缓冲全程在 cache 里被反复覆写，**写它不产生任何
    DRAM 流量**；512 MB 是每字节只写一次的冷区，每次写要先 RFO（把 64B 行从 DRAM 读
    进来），整份快照因此多出约 **316 MB** 的 DRAM 流量（158 读 + 158 写回）≈
    95 ms 里多背 3.3 GB/s 内存带宽。
16. **量级必须分开说**：缺页那一段是 **40×**，冷目的地这一段是 **1.2×**
    （1999.50 → 1669.22）。两个数差两个数量级，不能合进同一句话。
17. **但这个对照还不是单变量。** 除接收缓冲外，`--discard` 腿与项目腿之间还有几处
    没控住：recv 分块（64 KB vs 1 MiB —— 前者多付 2265 次 syscall 仍拿到 93.5%，
    方向**相反**）、从端进程形态（裸组件 vs 完整 kvstore）、主端进程形态（裸组件 vs
    kvstore fork 出的数据面子进程）、主端文件新鲜度（老文件 vs 刚被 `rdb_save_sync`
    写出、脏页可能仍在回写，方向**相反**）、尾部同步（服务端等 FIN vs 不等 FIN，
    方向**相反**）。要坐实第 15 条，需要给组件客户端加一个"大缓冲 + 预触 + 不落盘"
    的模式，与现在的 64 KB `--discard` 腿**同轮交替**跑 —— 那才是只剩缓冲一个变量的对照。
18. **"从机压主机"的机制**：从端每字节成本高 → 接收窗口填满 → TCP 通告窗口收缩 →
    主端 `sendfile` 阻塞在发送缓冲上。所以从端的开销 **1:1** 反映到主端 `rate`，
    两端计时只差 2~2.5% 就是传导在毫秒级完成的证据。这也是"速率一律以发送端为准"
    这个口径依然成立的原因 —— 主端那个 rate 就是瓶颈速率。
19. **RDMA 侧对预触/大页都不敏感，机制同源。** RDMA 从端是在 `rdma_reg_write` 里注册
    接收缓冲的，注册过程就把页全建立/钉住了，且发生在计时窗口之外 —— **等于自带预触**。
    所以它的瓶颈只剩 rxe 软件路径。**sendfile 的从端对 CPU/页敏感，RDMA 的从端对
    网卡敏感，两条路的优化方向不通用。**
20. **RDMA 这条路已经到顶，不必再动；单条大 WR 传整份 RDB 有依据。** 器件顶中位
    209.18（六格 198.18~213.04，散布 1.08×），项目 201.83 落在**带内**，差 <4% 且
    小于顶自身的散布。同时 `-t 1` 与 `-t 128` 打平 ⇒ 分块数不是杠杆：**"不分块"既
    没有代价，又省掉 151 次 post / completion 与往返**。
21. **在本机 RDMA 比 sendfile 慢 10.5 倍**（209 vs 2138 MB/s），这是 soft-RoCE 的
    价钱、不是代码问题。⇒ 本机的取舍依据不能是"哪个快"；也**别把本机的结论外推到
    真 RDMA 硬件**。

### 3.4 一句话总结

sendfile 全量同步的关键不在主端、也不在网线上，在**从端接收缓冲**：冷页让缺页落在
`recv` 途中，经 TCP 反压把主端拖到几十 MB/s（40×）；把缺页挪出窗口、并且让目标区不是
512 MB 的冷区，才回到零拷贝顶的 93.5%。**大页不是必需品，RFO 才是最后那 15%。**
RDMA 那条路已顶到 rxe 的软件天花板（209 MB/s，项目落在带内），单条大 WR 传整份 RDB
没有代价 —— 本机两条路都没有进一步优化的空间。
