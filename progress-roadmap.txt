Roadmap (revised 2026-05-16, supersedes progress-phase4.txt)
=============================================================

Goal: 8-core box → ~2.5-3.0M QPS, with each phase having explicit
correctness boundary and a measurable before/after.  Each phase is a
small, reversible step that "lays the groundwork" for the next one
rather than chasing peak numbers.

Phase 4 — Multi-thread proactor + dict sharding   [DONE]
========================================================
  [x] 32-shard kv_dict + per-shard pthread_rwlock
  [x] kvs_dispatch SHARD_WRLOCK guard via __cleanup__
  [x] DEL/EXISTS/MGET/MSET/MSETNX per-key shard locks
  [x] proactor: per-worker io_uring + buf_ring, SO_REUSEPORT
  [x] kvs_config.threads
  [x] bench_phase4.sh + perf table

  Result on 6c: t=1 → 360k, t=2 → 461k, t=4 → 439k, t=8 → 393k.
  Optimal t=2 (1.28-1.40x).  t≥4 regress because of core contention
  with the bench client + softirq — unlocked in Phase 5.

Phase 4B — Correctness completion (no perf target)   [DONE 2026-05-17]
======================================================================
Make every feature work under threads>1 so subsequent perf phases
don't trip over a "BLPOP / AOF reload broken in MT mode" pothole.

  [x] 4B.1  Auto threads + startup sanity warn  (DONE 2026-05-16)
        - kvs_config.threads default 0; resolved in config_postprocess
        - 0 → max(1, nproc-1); banner shows [auto]/[manual] + nproc + shards
        - 3 warnings: nproc oversubscribe / shard contention (8x rule) /
          cgroup cpu.max overrun
        - Verified on 6c box: threads 0 → "Workers: 5 [auto] (nproc=6)"
                              threads 1 → "single-thread proactor"
                              threads 64 → both warnings fire

  [x] 4B.2  block subsystem MT-safe  (DONE 2026-05-17)
        - g_block_mu coarse mutex around block_table; two-phase
          block_check_timeouts (collect under lock, deliver outside)
          to avoid recursive lock + notify-under-lock
        - struct conn gains owner_worker_id set on accept
        - per-worker pending wake queue (wake_head + wake_mu) + eventfd;
          cross-worker notify enqueues + writes 1 to target evfd, target
          worker handles EVENT_WAKE CQE and drains queue
        - new proactor_kick_worker(id) so BLPOP register can prod
          worker 0 to recompute block_nearest_timeout immediately
        - BLPOP deadline uses get_time_now_real() instead of cached ms
          (only worker 0 updates the cache; stale cache caused early
          timeout firing)
        - dropped `if (g_n_workers == 1)` guard on block_set_notify_cb
        - Verified t=4 (smoke /tmp/blpop_test.sh):
            * BLPOP 2s timeout on empty list  → 2020 ms, nil reply
            * Pre-pushed list, BLPOP returns immediately
            * BLPOP on conn A, RPUSH on conn B (different worker) →
              cross-worker wakeup ~28 ms after push
        - Perf bench at t=2 still in 380-450k SET range; revisit after
          Phase 5 pinning with proper isolation

  [x] 4B.3  AOF / WAL / sockmap_record MT-safe  (DONE 2026-05-17)
        - root cause: wal_repl.c journal ring was SPSC; multiple
          proactor workers racing on (g_jhead load, slot fill, store)
          would lose entries and corrupt slots
        - fix: g_journal_producer_mu guards the slot reservation +
          fill + g_jhead publish; eventfd write stays outside the mutex
        - aof_async_append → wal_repl_append, so this single fix covers
          both "persistence aof" and "rdma_sync on" paths
        - sockmap_record_cmd untouched: BPF per-CPU maps are MT-safe
          by construction
        - Default-config bench (persistence=none, rdma_sync=off):
          mutex never acquired (early-return on g_running==0), perf
          unchanged at 394k/395k SET/GET, t=2
        - Verified t=4 + persistence aof:
          200k SETs across 50k random keys → DBSIZE=49064 pre and
          post restart, sampled key values round-trip cleanly

  [x] 4B.4  RDB BGSAVE: point-in-time snapshot under MT  (DONE 2026-05-17)
        - root cause #1: fork() in MT mode inherits any held shard
          wrlock state into the child; the child is single-threaded
          and would deadlock on the first kv_shards_iter rdlock attempt
        - root cause #2: walking shards with per-shard rdlock yields a
          per-shard but not cross-shard consistent snapshot
        - design: take ALL shard wrlocks → fork → parent unlocks
          immediately; child runs a no-lock iterator on its frozen
          COW image
        - new helpers in kv_dict:
            kv_shards_lock_all_for_snapshot()
            kv_shards_unlock_all_snapshot()
            kv_shards_iter_init_nolock()
        - persistence.c: g_rdb_in_fork_child flag flips shards_scan to
          the no-lock iterator inside the child
        - banner now logs: "BGSAVE started, child pid=N (snapshot stall:
          X ms acquire, Y ms total)"
        - Verified t=4, persistence rdb:
          * pre-load 18,914 keys, BGSAVE, concurrent writes during save
            grow DB to 29,985, reload yields 28,174 — within
            [pre, post] snapshot window  → point-in-time intact
          * snapshot stall: 0 ms wrlock acquire, 4 ms total (fork+release)
          * concurrent SET throughput during BGSAVE: 260k/s (no stall)
        - No regression on default-config bench: 436k/394k SET/GET, t=2

  [x] 4B.5  Document & verify rehash MT-safety  (DONE 2026-05-17)
        - audited: dict_rehash_step() called only from dict_add /
          dict_replace / dict_delete; all three are write APIs
        - dict_find() is read-only, never invokes rehash_step, safe
          under a shared shard rdlock (its existing comment already
          says so)
        - added MT-safety contract block on dict_rehash_step in
          kv_dict.c:133-148 explicitly stating "MUST run with the
          owning shard's wrlock held" — locks the contract before
          Phase 6.2 splits read paths to rdlock
        - no code change required; current dispatcher uses SHARD_WRLOCK
          on every keyed command so the contract is automatically
          satisfied

  [x] 4B.6  test/bench/multi_thread_smoke.sh   (DONE 2026-05-17)
        - 12 checks under threads=4, all PASS:
          banner, STRING SET/GET/DEL, HASH/LIST/SET/ZSET basic ops,
          BLPOP timeout, BLPOP cross-worker wakeup, AOF reload
          (24,416 keys round-trip), RDB BGSAVE (26,295 in [12,634,
          29,383] window), snapshot stall log present
        - this script is the gate: any future Phase 4B-touching
          change must keep "Phase 4B smoke results: PASS=12  FAIL=0"

Phase 5 — CPU affinity (the real perf jump)   [in progress]
===========================================================
  [x] 5.1  pthread_setaffinity_np per worker  (DONE 2026-05-17)
        - config: cpu_pin {off|auto|N,N,N} parsed in config.c
        - default mode = auto; defaults respect what 4B.1 already set up
        - worker_pin_self() called at top of worker_loop BEFORE
          io_uring init, so the ring binds to the right NUMA / cache
          domain from creation
        - auto rule: worker_i -> core ((i+1) % nproc).  Core 0 left
          for kernel softirq + system; bench / client lives wherever
          it wants
        - banner now shows "CPU pin : auto (worker i -> core ...)"
          plus per-worker "[proactor] worker N pinned to core M"
        - Verified on 6c box, t=4 + cpu_pin auto:
          per-thread Cpus_allowed_list = 1, 2, 3, 4 (one core each)
        - Perf sweep, persistence=none, c=400 P=10 --threads 6:
          t=1  off=330k  auto=282k  (-15%, single worker locked away
                                     from where roaming softirq lands)
          t=2  off=437k  auto=435k  (tie)
          t=4  off=439k  auto=429k  (-2%)
          t=5  off=435k  auto=437k  (tie)
        - Conclusion: pinning alone is essentially neutral on
          loopback because bench/softirq still roam across cores.
          The pay-off lands when 5.2 pins IRQs/softirq AWAY from
          worker cores so workers get exclusive cycles.  The previously
          observed t>=4 regression is gone either way (4B already
          smoothed it out).

  [x] 5.2  tools/setup_affinity.sh  (DONE 2026-05-17)
        - new script: stops irqbalance, walks /proc/irq/*/smp_affinity
          and writes a hex mask for the chosen cores (default: core 0)
        - also writes /sys/class/net/*/queues/rx-*/rps_cpus so loopback
          softirq lands on the IRQ cores rather than the worker cores
        - flags: --cores N,N --iface NAME --restore
        - mask math validated (cores [0]->0x1, [0,5]->0x21, [1,2,3,4]->0x1e)
        - actual /proc write needs root, untested in this session;
          run on a server-only box during Phase 5 perf re-test

  [x] 5.3  kv_shard_t cacheline isolation re-check  (DONE 2026-05-17)
        - measured: pthread_rwlock_t=56, kv_dict_t=64 → 120 base
        - before: trailing _pad[64] → sizeof=184, align=8;
          adjacent shards COULD share cachelines
        - after: _pad[8] + __attribute__((aligned(128))) → sizeof=128,
          align=128.  Each shard owns exactly 2 cachelines exclusively,
          defeating Intel L2 spatial prefetcher's 128-byte stride
        - _Static_assert pins sizeof + alignof at build time so any
          future struct change that breaks isolation fails to compile
        - 4B.6 smoke regression: PASS=12 FAIL=0 (unchanged)
        - perf-c2c on this loopback box is too noisy to be conclusive
          for false sharing; will revisit on a quieter machine
  [x] 5.4  NUMA-aware buf_ring allocation skeleton  (DONE 2026-05-17)
        - new header src/core/numa_alloc.h with three helpers:
            kvs_numa_alloc_local(size)
            kvs_numa_free(p, size)
            kvs_numa_bind_local(addr, size)   ← used in proactor.c
        - compile switch -DKVS_USE_NUMA=1 (default 0); when unset, all
          helpers reduce to plain libc malloc/free or no-op
        - proactor.c: per-worker buf_base mmap now followed by
          kvs_numa_bind_local() so on multi-socket machines the buf
          ring is on the worker's local NUMA node from creation
        - skeleton only; on this single-NUMA box behaviour is identical
          to before.  Verified by 4B.6 smoke: PASS=12 FAIL=0
        - to enable on big machines: rebuild with
            cmake -DCMAKE_C_FLAGS="-DKVS_USE_NUMA=1" + link -lnuma

Phase 5 — exit criteria
=======================
  Status: 5.1-5.4 all DONE.  On this 6-core loopback box pinning is
  perf-neutral because bench client + softirq still roam.  The structural
  work (per-worker pin, IRQ script, cacheline isolation, NUMA hook) is in
  place and zero-regression; the actual perf jump will land when run on
  a server-only machine with 5.2's IRQ script applied.

  Expected on 8c box (workers cores 1..7, IRQ core 0, client elsewhere):
    t=7 → 1.5-2.0M    (matches old plan's "Phase 4" target)
  Expected on 6c box, same setup:
    t=5 → 1.0-1.4M

Re-plan (2026-05-17) — split into "do-now on 6c" and "wait-for-bigger-box".
The principle: any work that is pure single-core CPU savings or correctness
must be done on the current 6c box, because it will benefit every worker
equally once we move to a larger machine.  Anything that requires real
NICs, more cores, or multi-NUMA waits.

Phase 6 — Single-core dispatcher efficiency
============================================
Each item is core-count independent.  Each worker on the future big box
inherits the same speedup, so doing this on 6c first is correct.

  [x] 6.1  Eliminate double dict_find — STRING engine done  (DONE 2026-05-17)
        - root cause: string_cmd received `entry` from dispatcher but did
          `(void)entry;`, then engine_set_raw/engine_get_raw re-hashed
          and re-dict_find'd from scratch on every SET/GET/INCR/etc.
          Dispatcher also already cleared expired entries, making the
          expire-check inside engine_get_raw redundant
        - signature change: string_cmd(cmd, entry, hash, args, ...)
          plumbs both pre-computed pieces through
        - new engine_set_pre() / engine_get_pre() use the pre-found
          entry directly; engine_*_raw remain as thin wrappers for the
          MGET/MSET batch paths in kvstore.c (no pre-found entry)
        - Verified on 6c, persistence=none, c=400 P=10 t=6:
            t=1 SET 330k → 396k  (+20%)
            t=1 GET 304k → 396k  (+30%)
            t=2 SET 491k → 491k  (tie — already bench-bound)
            t=4 SET 434k → 438k  (tie)
        - 4B.6 smoke regression: PASS=12 FAIL=0 unchanged
        - Snapshot saved as test/bench/snapshot_phase6.1_*.txt;
          baseline file made write-protected (capture script now
          needs --baseline to overwrite)
        - HASH/LIST/SET/ZSET engines still have the same pattern;
          deferred to 6.1b (lower priority, those aren't the hot path
          on the SET/GET-dominated benchmark)

  [ ] 6.2  Split read-only commands to rdlock
        - strict-RO  (rdlock only):
            STRLEN HLEN HEXISTS HKEYS HVALS LLEN LINDEX SCARD SMEMBERS
            SISMEMBER ZCARD ZSCORE ZCOUNT TYPE EXISTS DBSIZE
        - lazy-expire-RO (rdlock-then-upgrade):
            GET HGET LRANGE SMEMBERS ZRANGE  — read under rdlock; if
            entry found expired, drop rdlock, take wrlock, re-check,
            then expire + return nil
        - 6c can't fully show the gain (heavy shared-shard rdlock
          contention needs many workers), but code is ready for
          big-box scaling validation

  [ ] 6.3  perfect-hash command dispatch (gperf) — gated by perf top
        - only do if `perf top` of running kvstore shows command-name
          comparison in top 10; otherwise skip

  [ ] 6.4  per-shard incremental rehash batching
        - currently dict_add/del runs `dict_rehash_step(d, 1)`;
          change to `dict_rehash_step(d, REHASH_BATCH)` where
          REHASH_BATCH = 8.  Amortises rehash cost when many writes
          arrive at the same shard

Phase 9 — BPF acceleration (replaces old "6.5 XDP")
====================================================
Two-step, gated by observed cache hit rate.

  [ ] 9.0  cache-hit observability prog
        - 30-line BPF prog that just counts (GET requests with key
          length ≤ 32 AND previously SET) over real workload
        - run overnight; need ≥30% to justify any further work

  [ ] 9.1  sockmap + sk_skb short-path (the "easy half")
        - sockmap_kvs.kern.c upgraded from observation-only to a
          BPF_SK_SKB_STREAM_VERDICT program that:
            * parses incoming RESP frames in kernel (one frame per
              verdict callback — kernel handles TCP reassembly)
            * looks up short hot key in BPF kv_hot_cache map
            * on hit: bpf_sk_redirect_map to a userspace fast-reply
              socket, bypassing kvs_dispatch + shard locks
            * on miss: SK_PASS, unchanged path
        - kvstore.c SET hook populates kv_hot_cache when key ≤ 32B
          and value ≤ 256B; DEL/expire removes
        - works on loopback, ~5-15% expected, zero correctness risk

  [ ] 9.2  XDP_TX zero-syscall path (the "hard half")
        - only after 9.1 stable and cache hit rate ≥ 60%
        - xdp_kvs.kern.c: parse RESP, lookup cache, XDP_TX a fully
          formed TCP reply, mark socket bytes for userspace drain
        - sock_ops prog tracks per-conn ISN + 5-tuple
        - userspace consults kv_pending_drain before dispatch
        - needs real NIC to show benefit; loopback ≈ 0

Notes / risks
=============
  * threads vs shard ratio: shards ≥ 8×threads.  32 shards comfortable
    up to 16-worker; revisit at ≥32 cores.
  * NUMA: skeleton lands in 5.4; real validation in Phase 5-validate.
  * Old "sockmap accel +30%" was a myth (sockmap can't synthesize
    replies).  Real perf jump on hits comes from Phase 9.2 XDP_TX.
  * Phase 7.1 AOF-rewrite-bg is the only remaining "fork-based"
    software-stall item; the RDB equivalent was already done in 4B.4.
