# KVStore 10.0 — Performance Benchmark Results

**Test Date**: 2026-05-15（Pipeline / AOF 最新）/ 2026-05-09（其余项）
**Machine**: 192.168.30.135 (ens33, Intel Proactor), Soft-RoCE (rxe0)
**KVStore Binary**: `build/kvstore` (jemalloc, Release)

---

## 1. AOF Persistence Overhead (bench_aof.sh)

**测试日期**: 2026-05-15  
**参数**: N=100 万, C=50, P=20, d=16B，VM 环境 (ens33)

| 场景 | QPS (req/s) | AOF 开销 |
|------|-------------|----------|
| A. kvstore — 无持久化 | 290,529 | — |
| B. kvstore — AOF (WAL/incr.wal) | 257,732 | **11.3%** |
| C. Redis — 无持久化 | 262,192 | — |
| D. Redis — AOF everysec | 171,674 | **34.5%** |

| 对比维度 | 结果 |
|---------|------|
| kvstore 无持久化 / Redis 无持久化 | **1.11×** |
| kvstore AOF / Redis AOF | **1.50×** |
| WAL 文件大小（100 万条 SET × 16B） | 150.7 MB（完整） |

**分析**:
- kvstore AOF 开销 **11.3%**，Redis AOF everysec 开销 **34.5%**，kvstore AOF 比 Redis AOF 快 **1.50×**
- WAL 100% 完整落盘（150.7 MB，无丢失），fdatasync 每秒执行一次（类 Redis everysec 语义）
- 低开销来源：WAL consumer 使用批量 writev（128 条/次系统调用），ring buffer 槽位内存精简至 128 B（L3 友好），无持久化路径上的主线程阻塞

### 优化历程（本轮）

| 阶段 | kvstore AOF 开销 | WAL 完整度 | 关键变更 |
|------|----------------|-----------|--------|
| 原始（AOF 静默失效） | -9.3%（假象） | ~1% | `g_stream_healthy=0` 使 AOF 成空操作 |
| Bug 修复后 | 78.8% | 63% | 修复三处 bug，AOF 真正工作 |
| 内存布局优化 | 58.1% | 86% | 槽位初始分配 4096→128 B，堆 576MB→18MB |
| **批量 writev（当前）** | **11.3%** | **100%** | 128 条/次 writev，syscall 减少 128× |

## 2. Pipeline 批量处理 (bench_pipeline.sh)

### 最新数据（2026-05-15）

100 万请求/轮, 50 并发, d=16B，测试环境: VM (ens33).

| Pipeline | kvstore SET | Redis SET | S倍率 | kvstore GET | Redis GET | G倍率 |
|----------|------------|-----------|-------|------------|-----------|-------|
| P=10 | 139,997 | 167,364 | 0.84x | 160,077 | 190,512 | 0.84x |
| P=20 | 287,770 | 265,041 | **1.09x** | 282,486 | 321,027 | 0.88x |
| P=40 | 472,144 | 379,795 | **1.24x** | 462,107 | 424,628 | **1.09x** |
| P=80 | 580,383 | 448,029 | **1.30x** | 637,349 | 508,647 | **1.25x** |
| P=160 | 683,995 | 445,038 | **1.54x** | 709,220 | 545,256 | **1.30x** |

- **P≥20 后 kvstore SET 反超 Redis**，与预期一致
- Redis SET 在 P=80 → P=160 几乎饱和（448K → 445K），kvstore 仍持续增长（580K → 684K）
- GET 比值略低于 SET 比值，因为 Redis GET 路径极度优化（哈希表直接命中），属正常差异
- 低 Pipeline（P=10）kvstore 落后约 16%，符合预期——proactor 的批处理优势在低并发下不显著

## 3. SAVE 性能影响 (bench_save.sh)

**测试日期**: 2026-05-15  
**参数**: N=200 万, C=50, P=20, d=16B，VM 环境 (ens33)

三种场景对比:
- **场景 A（基线）**: 纯 SET，不触发任何 SAVE
- **场景 B（BGSAVE 异步）**: 每 3s 触发一次 BGSAVE，fork 子进程写盘，主线程继续服务
- **场景 C（同步等待 SAVE）**: 每 20 万条命令触发一次 SAVE 并等待完成（共 10 次），测量含 SAVE 等待的端到端 QPS

| Key 数量 | A 基线 QPS | B BGSAVE QPS | B 降幅 | C 同步SAVE QPS | C 降幅 | RDB 大小 | 单次SAVE耗时 |
|----------|-----------|-------------|--------|--------------|--------|---------|------------|
| 10,000   | 286,000   | 303,998     | **<5%**¹ | 192,400  | 32.7%  | 0.4 MB  | 275 ms     |
| 100,000  | 291,928   | 303,444     | **<5%**¹ | 195,561  | 33.0%  | 4.1 MB  | 270 ms     |
| 1,000,000| 283,970   | 302,663     | **<5%**¹ | 97,518   | 65.7%  | 41.0 MB | 1,319 ms   |

> ¹ 场景 B 实测数字略高于基线（-3~-7%）属于单次测量噪声（±5%）。真实 BGSAVE 影响来自 COW（写时复制）压力，在 VM 环境约 1-5%。

**场景 C 降幅分析:**

| Key 数量 | 10 次SAVE总等待 | benchmark时间 | 总耗时 | C降幅来源 |
|----------|--------------|-------------|-------|---------|
| 10k / 100k | 10 × 275ms = 2.75s | ~7s | ~9.75s | **fsync 固定延迟**（与数据量无关） |
| 1M        | 10 × 1319ms = 13.2s | ~7s | ~20.2s | **io_uring 写 41MB + fsync** |

- **BGSAVE（生产用法）对主线程 QPS 几乎零影响**: fork 子进程完全异步，io_uring 写盘 + fdatasync 在独立进程中完成
- **同步等待 SAVE 的 270ms 固定耗时**来自 VM 虚拟磁盘 `fdatasync` 刷盘延迟，与 RDB 数据大小无关（0.4MB 和 4.1MB 耗时相同）；物理 NVMe 下约 1-10ms
- **1M keys 单次 1319ms** = 写入 41MB 数据（io_uring，约 ~30ms）+ fdatasync（约 ~1290ms，VM 磁盘 flush 大文件较慢）

## 4. 内存分配器对比 (bench_memory.sh)

50 万 key × 64B value. 测试 jemalloc (默认) vs glibc malloc.

| 分配器 | 阶段 | VmSize (MB) | VmRSS (MB) |
|--------|------|-------------|------------|
| **jemalloc** | 空闲 | 22.5 | 6.6 |
| **jemalloc** | 峰值 | 101.5 | 69.8 |
| **jemalloc** | FLUSHALL 后 | 101.5 | 69.7 |
| glibc | 空闲 | 1,033.0 | 3.9 |
| glibc | 峰值 | 1,102.7 | 73.5 |
| glibc | FLUSHALL 后 | 1,102.7 | 73.5 |

- **jemalloc 空闲 VmSize 仅为 glibc 的 2.2%** (23 MB vs 1,033 MB)
- glibc 的高 VmSize 源于 arena per thread 设计——即使空闲也预分配了大量虚拟地址空间
- 峰值 VmRSS: jemalloc 70 MB vs glibc 74 MB — jemalloc 节省 ~5%
- 两者均不主动归还内存给 OS (FLUSHALL 后 RSS 不变)，属于 glibc/jemalloc 的默认行为

## 5. 实时同步 QPS 损耗 (bench_sync_qps.sh)

50 万请求/轮, 50 并发. 复测验证：kvs-on 三轮波动 <1%，数据可复现.

### P=20

| 场景 | SET/16B | SET/256B | SET/1024B | GET/16B | GET/256B | GET/1024B |
|------|---------|----------|-----------|---------|----------|-----------|
| kvstore 关闭复制 | 306,373 | 220,946 | 114,443 | 286,205 | 268,097 | 294,464 |
| kvstore eBPF 复制 | 68,615 | 63,428 | 48,003 | 298,329 | 307,692 | 297,442 |
| Redis 关闭复制 | 266,241 | 245,700 | 167,504 | 319,898 | 277,932 | 207,297 |
| Redis 主从复制 | 208,681 | 165,508 | 109,218 | 321,337 | 279,642 | 209,996 |

### P=80

| 场景 | SET/16B | SET/256B | SET/1024B | GET/16B | GET/256B | GET/1024B |
|------|---------|----------|-----------|---------|----------|-----------|
| kvstore 关闭复制 | 641,026 | 428,449 | 139,392 | 655,308 | 853,242 | 704,225 |
| kvstore eBPF 复制 | 78,864 | 71,134 | 56,016 | 658,762 | 746,269 | 552,486 |
| Redis 关闭复制 | 408,163 | 286,533 | 163,185 | 449,236 | 419,815 | 256,542 |
| Redis 主从复制 | 274,123 | 210,438 | 110,717 | 484,966 | 441,306 | 275,482 |

### SET QPS 损耗 (P=20, d=16B) — 3 轮复测验证

| | 关闭复制 | 开启复制 | 损耗 | 轮间波动 |
|--|---------|---------|------|---------|
| **kvstore** | 306,373 | 68,615 | **77.6%** | <1% |
| Redis | 266,241 | 208,681 | 21.6% | — |

- **GET 不受复制影响**: 读操作不触发 eBPF uprobe，QPS 完全保持
- **kvstore SET 损耗较高 (77.6%)**: eBPF uprobe 在每次 SET 时同步捕获命令并写入 ring buffer。该损耗来源于内核态 uprobe 开销 + 用户态 ring buffer 消费。这不是 bug，而是当前 eBPF 同步捕获路径的设计代价
- Redis master-slave SET 损耗 21.6%，因为它使用内置的 replication buffer（纯用户态），没有内核态切换
- 优化方向: 批量 ring buffer 消费、零拷贝 ring buffer → TCP 传输、eBPF tail call 减少 uprobe 次数

## 结果是否符合预期

| 发现 | 是否符合预期 | 说明 |
|------|------------|------|
| kvstore AOF 开销 11.3% vs Redis 34.5% | **优于预期** | 修复三处 bug（ring 溢出 + 永久禁用 + 阻塞 fdatasync）+ 批量 writev 后，kvstore AOF 比 Redis AOF 快 1.50×。主要优化：槽位内存 576MB→18MB（L3 友好），128条/次批量 writev |
| Pipeline P≥20 后 kvstore 反超 Redis | 符合 | proactor 多线程事件循环天然适合高吞吐批处理 |
| Redis SET 在 ~400k 饱和 | 符合 | Redis 单线程模型瓶颈 |
| BGSAVE 几乎不影响 QPS (<5%) | 符合 | fork 子进程异步写盘，COW 压力在 VM 下约 1-5%，单次测量噪声 ±5% |
| jemalloc VmSize 远小于 glibc | 符合 | glibc arena-per-thread 设计的已知特征 |
| 同步 SET 损耗 77.6% | 偏高但可解释 | eBPF uprobe 同步捕获是当前实现路径，每条写命令都经过内核态 uprobe → ring buffer → 用户态消费。Redis 的 21.6% 是纯用户态 replication buffer |

**注意**: 当前 kvstore 主从同步的 eBPF 实现是功能正确性优先的版本（已验证 20/20 主从同步测试通过），性能优化是后续工作。
